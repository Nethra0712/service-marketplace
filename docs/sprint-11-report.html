3–4 Security & correctness findings

From three focused audits (authentication/authorization/injection/CSRF/CORS/rate-limiting/secrets; financial integrity and concurrency; test-coverage gap analysis) plus manual follow-up. Ordered by severity. Every finding below was fixed this sprint unless marked otherwise, and every fix was verified against the full test suite afterward.

Medium–HighPayout calculation wasn't transactionalFixed
Financial integrity · payments.service.ts

Scenario: calculatePayoutsForPeriod inserted a payout row, then separately stamped its payments with that payout's id. A crash between the two left a payout row that looked final — the function's own idempotency check would skip that provider on every future recompute — while the underlying payments were never marked as swept into it. Those payments would then be silently, permanently excluded from any payout, with no error anywhere.

Fix: both writes now run inside a single db.transaction, per provider.

MediumAdmin login had no per-account lockoutFixed
Authentication · admin-auth.service.ts

Scenario: the only defense against password guessing was a per-IP rate limit (10 attempts / 15 min). An attacker distributing guesses across many source IPs faced no account-level limit at all.

Fix: added a database-backed per-account lockout — 10 consecutive failures locks the account for 15 minutes, timing-consistent with the existing unknown-email/wrong-password path so a locked account can't be distinguished from a merely-wrong-password one by response time. A locked-out account's lock is never extended by further attempts (a fixed window, not sliding), so hammering a locked account can't be used to keep it locked indefinitely.

MediumRefund calls the gateway before persisting stateDocumented, not code-fixed
Financial integrity · payments.service.ts · payhere-payment-provider.ts

Scenario: a crash between the gateway refund call succeeding and the local DB write committing would leave the payment looking un-refunded; a retry (the natural recovery action) would call the gateway a second time.

Why not fixed in code: PayHere's real Refund API is not wired up in this codebase — PayHereProvider.refund always rejects with a clear error. Only the mock provider can reach this path today, so the risk is currently dormant, not live. Documented in docs/INCIDENT_RESPONSE.md with a note to add a gateway-side idempotency key when real refunds are implemented.

MediumReal bug: tracking never rejoined after a reconnectFixed
Reliability · Mobile · tracking_providers.dart

Scenario: found via the coverage-gap audit, not the security audits. Socket.IO room membership lives on the connection itself. After any network blip, the client's socket reconnects with a brand-new underlying connection — the server has silently forgotten the room — but the app never rejoined it. The UI's connection badge would correctly flip back to “Live”, while location updates for that booking would stay dark for the rest of the session.

Fix: BookingTrackingController now detects a genuine reconnect (a disconnected state, however many connecting retries follow, landing on connected) and rejoins the room automatically — while correctly not re-joining on the very first connect, which is already handled. Two new widget tests cover both the connection-state UI transitions and the actual rejoin call.

LowTwo more payment writes weren't transactionalFixed
Financial integrity (audit-trail only) · payments.service.ts

Scenario: createPaymentRow (the insert + its ledger entry) and the success path of handleCallback (the status transition + its ledger entry) were each two separate statements. A crash between them would leave the payment's own status column — the actual source of truth for idempotency everywhere else in the system — correct, but with a missing ledger entry for that one event: an audit-trail gap, never a double-processing or money-safety issue.

Fix: both pairs now run inside a single transaction each.

LowA concurrent dispatch wave could drop legitimate offersFixed
Concurrency · bookings.repository.ts

Scenario: insertOfferWave did one multi-row insert and caught-and-swallowed unique-violation errors from the whole statement. A partial collision (some candidate rows new, one colliding with a concurrent dispatch for the same booking) failed and discarded the entire wave, including the legitimately-new candidates, not just the colliding one.

Fix: switched to onConflictDoNothing(), which Postgres applies per-row on a multi-row insert — only the actually-colliding rows are skipped.

InformationalLive-location cache was never wired to booking lifecycle eventsFixed
Reliability (memory hygiene, not a privacy leak) · app.ts · bookings.service.ts

Scenario: the realtime module's forgetBooking cleanup hook was built but its return value was discarded in server.ts — nothing ever called it. Not a privacy issue: every room join and location update independently re-validates the booking's live database status, so a stale cached location could never actually reach anyone. It was purely an unbounded in-memory growth risk for a long-running process.

Fix: wired via a forward-reference (the realtime module is necessarily constructed after the Express app, which needed a small indirection) into booking completion, cancellation, release, and matching-window expiry.

InformationalNon-constant-time webhook signature comparisonFixed
Authentication · payhere-payment-provider.ts

The PayHere callback signature check used !== on two strings. Theoretical timing side-channel; very low practical risk given MD5-over-HTTPS with a random merchant secret. Switched to the codebase's existing timingSafeEqual-backed safeEqual helper, already used for OTP and CSRF comparisons.

InformationalPayment webhook had no rate limitingFixed
Rate limiting · payments.routes.ts

By necessity — it's an unauthenticated gateway callback endpoint, so it can't require a session. Signature verification is the real protection against state-changing abuse; the gap was a minor request-flooding surface. Added a generous IP-based limit (300/min) as defense-in-depth, sized so it won't interfere with the gateway's own legitimate traffic from its small pool of server IPs.

InformationalAdmin logout wasn't CSRF-protectedFixed
CSRF · admin-auth.routes.ts

Every other mutating admin route required the CSRF header; logout didn't. Not actually exploitable — the session cookie's SameSite=Strict already stops it being sent on a cross-site request at all — but inconsistent. Added requireCsrf for consistency, with a regression test proving the session survives a CSRF-missing logout attempt.

InformationalNo test proved admin sessions expire naturallyFixed
Test coverage · auth.test.ts

Only logout-revocation and a forged/garbage cookie were tested; nothing advanced the clock past a session's natural lifetime. Added both a just-before-expiry (still works) and just-after-expiry (rejected) test.

✓ Reviewed and confirmed clean

Checked against actual code, not inferred from naming — each of these was verified by reading the relevant handler, schema, or query, not assumed.

✓ Authentication bypass — every protected route gated, JWT algorithm/issuer/audience pinned, DB-checked on every request
✓ Authorization bypass / IDOR — every owned resource scoped to the caller; a booking/payment/review/application that isn't theirs 404s
✓ SQL injection — no raw string-concatenated SQL anywhere; the few sql\`\` uses are parameterized
✓ XSS — pure JSON API; no user input is ever interpolated into an SMS/notification template
✓ Insecure CORS — explicit origin allow-list, never wildcard + credentials
✓ OTP abuse — CSPRNG codes, HMAC-hashed at rest, 5 attempts/challenge, 5 challenges/hour/phone, advisory-locked against races
✓ Token leakage — Authorization/cookie headers redacted in logs; no token ever logged in application code
✓ Refresh-token reuse — a replayed token revokes the whole session family, not a silent reissue
✓ Sensitive logging — no password, OTP code, or full JWT logged anywhere; mock-SMS OTP-in-log is explicitly production-refused
✓ Admin privilege escalation — no HTTP path creates an admin account; no route accepts a caller-supplied role field
✓ Mass assignment — z.strictObject allow-lists throughout; price/status/verification fields are never client-writable
✓ Unsafe file uploads — no upload capability exists anywhere in the codebase
✓ Duplicate payment / payout prevention — enforced at the database level, not just application logic
✓ Booking double-acceptance — DB-level conditional update + unique index, verified with real concurrent requests
✓ Server-side commission & pricing — never client-supplied, anywhere, for any pricing model
✓ Rounding correctness — commission + provider earning always sum exactly to the service amount, by construction
✓ Financial record immutability — ledger and payout totals are never updated after insert
✓ Location privacy — no history persisted; room join re-validated against live status; tracking self-heals on every access

5 Remaining risks

  • Refund/gateway crash window — dormant until PayHere's real Refund API is implemented; needs a gateway-side idempotency key at that point (see finding above).
  • Rate limiting is single-instance only — counters live in process memory; running more than one backend instance behind a load balancer makes every limit approximate until a shared store (Redis) replaces it.
  • Outdated transitive dependencies with moderate/high advisories, deferred pending major version bumps and (for firebase-admin) a push-delivery retest.
  • No dedicated load-testing tooling in this environment — concurrency correctness was verified with real parallel requests (see Performance below), but sustained-throughput numbers under hundreds of simultaneous users were not measured.

Database query plans

The provider-matching candidate query — the hottest path in dispatch — was checked with EXPLAIN ANALYZE against real indexes: confirmed to use provider_services_city_category_status_idx as an index scan, not a sequential scan, with the join to provider_profiles resolved by primary key. Index design for every other concurrency-critical query (booking acceptance, payment lookup by external reference, payout idempotency) was reviewed structurally in the financial-integrity audit and confirmed backed by the appropriate unique index — see docs/DATABASE.md.

Concurrency correctness

Not raw throughput, but the thing that actually matters here: every documented race condition was verified with genuine parallel requests (real Promise.all, not sequential steps dressed up as a race), and every one of them produces exactly one winner, every time:

  • Two and three simultaneous booking-accept attempts on the same offer wave, repeated across 10 trials
  • Simultaneous quote acceptance
  • Simultaneous OTP request volume-cap and simultaneous OTP guess attempts
  • Simultaneous refresh-token use of the same token
  • Simultaneous identical provider category applications
  • Simultaneous conflicting provider-review decisions

What wasn't measured

No dedicated load-generation tool (k6, Artillery, or similar) is installed in this environment, so sustained-concurrency throughput — hundreds of simultaneous bookings, payment callbacks, or location updates — was not measured under real load. The backend's own 942-test suite (heavy real-database I/O, a fresh app instance per file) completing in roughly 205 seconds is a rough proxy that nothing is pathologically slow, not a substitute for real load testing.

8 Deployment readiness

The application itself — authentication, authorization, the booking lifecycle, matching, payments and commission, payouts, reviews, notifications, and the admin dashboard — is thoroughly tested (1,435 passing tests, including real-concurrency races) and was security-audited this sprint against a standard vulnerability checklist, with every finding either fixed or explicitly documented as a deferred, low-exploitability risk.

What stands between this and a first production deployment is entirely operational: no backups, no CI, no monitoring, no deployed environment, and two concrete mobile release-signing steps. None of it is a defect in what's been built. The nine items in Production blockers are the honest, complete list.
